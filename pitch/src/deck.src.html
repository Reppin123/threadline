Problem

Customers answer texts. Brands talk to them through widgets and email.

The channel gap
5.6%

SMS campaign click rate

1.69%

email campaign click rate

Text gets about 3x the clicks of email. Yet support and sales still live in a chat bubble on a website the customer has already left.

Why brands don't fix it

A text agent that is safe to put in front of customers needs five hard parts:

  • read the whole site and catalog, keep it fresh
  • take real actions (orders, bookings) through tools
  • remember each customer across conversations
  • test it before a customer sees a wrong price
  • iMessage plumbing, delivery, retries, routing
Click rates: Klaviyo 2026 SMS and email benchmarks, 183,000+ Klaviyo customers. klaviyo.com/products/sms-marketing/benchmarks · klaviyo.com/products/email-marketing/benchmarks
Shoppers read and answer texts; Klaviyo's own benchmarks show SMS campaigns get about three times the clicks of email. But a brand that wants a real two-way agent in texts has to build five things: ingestion, tools, memory, testing and the iMessage plumbing. Small brands can't. That's the gap.

How it works

Four agents behind every bot, so the customer never meets a first draft.

Builder agent

Reads the business

Sitemap crawl, JSON-LD, Shopify JSON, headless fallback. Writes persona, FAQs, guardrails, data tables and test questions. OpenAPI and MCP become tools.

→
Simulated customers

Try to break it

Typos, Hinglish, mind changes, prompt injection, plus the owner's test questions. Same runtime as production.

→
Judge agent

Grades every reply

Checks each claim against retrieved source pages. Wrong price or invented fact = fail, shown before deploy.

→
Runtime agent

Talks to customers

Knowledge search, per-customer memory, tables it fills (Orders), scheduling, human handoff, "I don't know".

Gateway

Photon Spectrum (iMessage) → per-sender ordered queue, burst debounce, retries → one core.chat() shared by iMessage, playground and tests. Immutable versions, so what passed checks is exactly what ships.

Source: packages/core (builder.ts, checks.ts, runtime.ts), apps/gateway. ARCHITECTURE.md in the repo.
Under the hood every bot is four agents. The builder reads the business. Simulated customers attack it with typos, mixed languages and injection attempts. A judge grades every reply against the source pages. Only then does the runtime agent face customers, with memory, tables and handoff. One chat function serves the playground, the tests and iMessage, so what we test is what ships.

Appendix A · Architecture

One container, three processes, one brain.

apps/web · Next.js 15

Landing and SEO pages, auth (magic link, password, Google), wizard, builder, deploy, data, conversations, stats, public API with keys.

apps/gateway · Photon Spectrum

iMessage cloud / local Mac / terminal modes, Telegram long polling, line_routes binding, per-sender queue, outbound scheduler, retries.

apps/worker

Durable job queue: build_bot, run_checks, recrawl. Concurrency 2, stale-job requeue, heartbeat.

packages/core

LLM provider abstraction, ingest (site, OpenAPI, MCP, idea), FTS5 retrieval, tools, memory, runtime loop, checks, judge, insights.

packages/db

SQLite (node:sqlite, WAL), migrations, job queue, AES-256-GCM credential encryption, snapshots to Supabase Storage every 30 s.

Hosting

Live on Cloudflare Containers. Same Docker image runs on Fly or Render. Scale path: Postgres + pgvector behind the same db helper.
